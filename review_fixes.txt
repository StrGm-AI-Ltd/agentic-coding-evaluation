# review.txt fix log (agentbench-trading-service-jls)

## 1. build.gradle.kts — Spring Boot version pinned in two independent places [maintainability/medium]
Root cause: `id("org.springframework.boot") version "3.5.5"` and `platform("...spring-boot-dependencies:3.5.5")`
were two unrelated literals; a partial upgrade of one silently desyncs the classpath.
Fix: introduced a Gradle version catalog (gradle/libs.versions.toml) with a single `springBoot` version
entry; both the plugin (`alias(libs.plugins.springBoot)`) and the BOM import
(`spring-boot-dependencies:${libs.versions.springBoot.get()}`) now resolve from that one entry.
Note: the BOM import had to stay — the Spring Boot plugin does NOT manage the unversioned
org.postgresql driver (verified: resolution fails without it).
Tests: full `./gradlew test` green.

## 2. build.gradle.kts — redundant testImplementation("org.postgresql:postgresql") [maintainability/low]
The test source set extends main, so the driver was already on the test classpath via `implementation`.
Fix: removed the duplicate coordinate. Tests (`JobQueueIT`, `ExperimentsServiceTest`,
`ImporterServiceTest` — all construct org.postgresql.Driver directly) still resolve it from
implementation; full `./gradlew test` green.

## 3. build.gradle.kts — unused H2 testRuntimeOnly dependency [maintainability/low]
Verified no test actually uses H2: the only occurrence is a string literal in PlanParserTest ("tables exist
in H2" sample data); every DB test hits real Postgres via jdbc:postgresql (local instance or
AB_JLS_TEST_DSN). A silently-active H2 fallback would mask misconfiguration, so it is removed.
Tests: `./gradlew test` green.

## 4. build.gradle.kts — CI=1 leaked to every Test task [maintainability/medium]
tasks.withType<Test> { environment("CI", "1") } also applied the variable to dockerTest (and any
future Test task); anything branching on CI (testcontainers pull/reuse logic, CI-gated flags) changed
behaviour there silently. Fix: the environment call now lives on tasks.named<Test>("test") only — the
task the agent harness actually runs - with a comment explaining the intent and the blast radius.
Tests: `./gradlew test` green.

## 5. gradle.properties — machine-specific JDK path committed [maintainability/high]
org.gradle.java.home pointed at one developer's Homebrew OpenJDK 21; every other machine/CI would
hard-fail. Fix: line removed from the repo. The build also has a Java 21 toolchain declaration, so
machines with any JDK 21 (on PATH / auto-detectable) work out of the box. For this machine - where
the shell's default java is 11 - the same pin now lives in the developer-local
~/.gradle/gradle.properties instead, so local builds are unchanged.
Tests: `./gradlew test` green (with the user-level pin in place).

## 6. gradle-wrapper.properties — retries=0 on the distribution download [maintainability/medium]
A single network blip during the ~200MB wrapper download hard-failed the build. Fix: retries=2
(paired with the existing retryBackOffMs=500). Not a code path, so no test run needed; wrapper
properties take effect on next distribution fetch.

## 7. docker_shim.sh — silent fall-through when the daemon never comes up [bug/high]
If all 90 poll iterations expired (Docker Desktop absent, app crash, OOM), the script unconditionally
logged "#ready 180s" and exec'd the real CLI, which then failed with a generic "cannot connect to the
Docker daemon" with no hint the shim tried. Fix: one final `docker info` check after the loop — on
success log #ready, on failure log #failed and exit 1 with an explicit stderr diagnostic.
Verified: `zsh -n` clean; `./gradlew test` green (shim is a harness resource, no unit test targets it).
